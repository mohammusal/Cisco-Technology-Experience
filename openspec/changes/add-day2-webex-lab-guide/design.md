# Design

## Context

See `proposal.md` for motivation and scope. The colleague delivered Day 2 as a packaged student handout at `C:\Users\mohamusa\Downloads\python-workshop` (165 files total, generated by `scripts/package.py`). That handout contains:
- **Raw source**: `code/day2/` (25 files), `guide/overrides/home.html`, `guide/overrides/partials/progress-map.html`, and `guide/stylesheets/extra.css`.
- **Compiled HTML only (no `.md` source)**: `guide/day2/*.html` (10 pages, 14 Mermaid diagrams, 11 tabbed blocks, 4 tables, 0 new screenshots) and `guide/help/{troubleshooting,glossary}.html` (+3 troubleshooting entries, +9 glossary terms).

The repository already builds and publishes via `mkdocs build --strict`, `scripts/check_code.py`, `scripts/package.py`, `scripts/check_diagrams.py`, and `.github/workflows/pages.yml`.

## Goals / Non-Goals

**Goals:**
- Reconstruct faithful, clean MkDocs Material Markdown for all 10 `docs/day2/*.md` pages so the rebuilt HTML matches the colleague's Day 2 content while inheriting our repo's exact CSS and theme.
- Keep `docs/day1/*`, Day 1 code/solutions, and `docs/stylesheets/*` completely untouched.
- Prevent `token.txt` from ever leaking into Git or `dist/python-workshop.zip`.
- Verify Day 2 student code offline inside `scripts/check_code.py` without requiring `webexteamssdk`, `flask`, `fastapi`, `uvicorn`, or internet access in GitHub Actions.
- Deliver a local preview via `mkdocs serve` before committing or pushing.

**Non-Goals:**
- Adopting the colleague's Day 1 edits (`lab0/hello.py` uncommented TODO, `lab2` cinema-to-zoo text) or `extra.css` palette overrides.
- Executing live Webex API calls or spinning up Flask/FastAPI servers in CI.
- Pushing to GitHub or publishing to GitHub Pages during this change before owner approval.

## Decisions

### D1. Reconstruct `docs/day2/*.md` from `guide/day2/*.html` with round-trip verification
- **Choice**: Parse `<article class="md-content__inner">` from each of the 10 compiled HTML files in `C:\Users\mohamusa\Downloads\python-workshop\guide\day2\` into clean MkDocs Material Markdown (`front matter`, `lab-summary`, `step-num`, admonitions/collapsible details, `===` tabbed blocks, fenced code blocks, tables, and verbatim `<pre class="mermaid"><code>` blocks), then verify the rebuilt HTML against the colleague's HTML (headings, step count, code block count, Mermaid diagram count, admonition count, and text content).
- **Alternatives considered**:
  - *Wait for the colleague's `.md` files*: clean, but blocks merging right now when the HTML already preserves 100% of the text, code, and raw Mermaid source.
  - *Embed pre-compiled HTML into `docs/day2/`*: breaks MkDocs search indexing, relative links, glossary tooltips, `hooks/search_exclude.py`, and future edits.

### D2. Preserve our repo's exact styling in `docs/overrides/home.html` and `docs/stylesheets/`
- **Choice**: Keep `docs/stylesheets/extra.css` (and all other CSS files) untouched. In `docs/overrides/home.html`, update only the hero lead copy, the two CTA buttons (`Start Day 1` / `Start Day 2`), and the 4 lower cards (replacing the redundant standalone Cheat Sheet card with the `Day 2 - Webex APIs` card while keeping Day 1's cheat sheet reachable in the `Python Basics` tab, matching the colleague's 4-card grid) without changing any CSS classes or colour rules in `home.html`.
- **Alternatives considered**:
  - *Copy colleague's `extra.css`*: rejected because the owner asked to follow this guide's existing styling and keep Day 1 styling untouched.
  - *Add a 5th card to the home page*: breaks the 4-column desktop / 2-column tablet grid symmetry.

### D3. Dual-day `progress-map.html` via `page.meta.day`
- **Choice**: Adopt the `day = page.meta.day | default(1) | int` branching pattern in `docs/overrides/partials/progress-map.html`. Day 1 pages do not set `day:` in front matter, so they automatically default to `1` and render byte-for-byte identically; Day 2 lab pages (`lab0-setup.md` through `lab7-fastapi.md`) set `day: 2` and `lab: 0..7`.
- **Alternatives considered**:
  - *Separate partial per day*: duplicates template markup and requires conditional logic in `main.html`.

### D4. Offline-only Day 2 checks in `scripts/check_code.py`
- **Choice**: Keep all Day 1 checks untouched and add a `check_day2()` group that:
  1. Verifies every Day 2 starter (`code/day2/lab*/*.py`) has numbered `# TODO ` markers (where applicable) and every `.py` file under `code/day2/` compiles cleanly via `ast.parse` / `py_compile`.
  2. Runs `code/day2/lab0/setup.py`, `code/day2/lab1/get_rooms.py`, `code/day2/solutions/lab1_get_rooms.py`, and `code/day2/solutions/lab1_exercise.py` in a temporary directory containing `rooms_sample.json` (standard library only, zero network calls) and checks expected output.
  3. Runs `code/day2/solutions/lab0_setup.py` without `token.txt` to verify `config.access_token()` exits with the friendly setup instructions, and with a fake `token.txt` (in a temp folder) to verify it loads and prints the masked prefix.
- **Alternatives considered**:
  - *Install `webexteamssdk`, `flask`, `fastapi`, `uvicorn` in `requirements.txt` and mock HTTP calls*: bloats CI installs and mixes student runtime dependencies with MkDocs build dependencies.
  - *Skip Day 2 in `check_code.py`*: risks shipping broken syntax or broken offline Lab 0/Lab 1 files.

### D5. Defence-in-depth for `token.txt`
- **Choice**: Ignore `token.txt` (and `code/**/token.txt`) in `.gitignore`, and add `"token.txt"` to `SKIP_IN_CODE` in `scripts/package.py`. Keep `code/day2/token.example.txt` tracked and packaged.
- **Alternatives considered**:
  - *Only `.gitignore`*: a student or instructor running `scripts/package.py` locally with a test `token.txt` present would accidentally ship their live Webex token inside `dist/python-workshop.zip`.

## Risks / Trade-offs

- **HTML-to-Markdown fidelity risk** -> Mitigate by running an automated structural comparison script between `C:\Users\mohamusa\Downloads\python-workshop\guide\day2\*.html` and the newly built `site/day2/*.html` (checking headings, code blocks, admonitions, tabs, tables, and Mermaid diagrams) plus visual inspection via `mkdocs serve`.
- **Glossary tooltips inside Day 2 prose** -> Adding the 9 Day 2 terms to `docs/includes/abbreviations.md` will also enable hover tooltips for words like `token` or `API` if they appear on any page. Check `docs/day1/` build output has no unintended formatting issues (and note `docs/day1/*.md` itself stays untouched).
- **Relative links between Day 2 pages and Help/Day 1** -> `mkdocs build --strict` catches every broken internal link automatically.
- **Colleague's `lab0-setup.md` vs `venv` guidance** -> Keep the colleague's Day 2 Lab 0 content intact during the merge; any wording alignment with Day 1's `.venv` section can be done later only if the owner asks after previewing locally.

## Migration Plan

1. Apply the change locally (copy `code/day2/`, create `docs/day2/*.md`, wire `mkdocs.yml`, `home.html`, `progress-map.html`, `troubleshooting.md`, `abbreviations.md`, `.gitignore`, `package.py`, `check_code.py`).
2. Run all verification commands locally (`check_code.py`, `package.py`, `check_diagrams.py`, structural HTML diff, `git diff` boundary check on Day 1 & CSS).
3. Launch `mkdocs serve` locally so the owner can review Day 1 and Day 2 in the browser.
4. Only after owner sign-off, commit and push to `origin/main` (which triggers `.github/workflows/pages.yml` automatically). Rollback if ever needed: `git revert HEAD && git push`.
